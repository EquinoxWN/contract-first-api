## Analyze: what the numbers show

- **The TypeSpec defaults do not meet the style guide.** The draft's 46 errors come from a few
  root causes, each repeated per operation or per field:
  - operationIds are `Interface_operation` (`Orders_list`) under the default
    `operation-id-strategy: parent-container`: 8 `cfa-operation-id-camel-case` errors;
  - field names were typed in snake_case and nothing stopped them: 5 `cfa-property-camel-case`;
  - list operations used `offset`/`page` with no bounds and returned bare arrays: 17 pagination
    errors over 3 list operations;
  - the TypeSpec `@error` model is emitted as an `application/json` `default` response, and no
    operation declares a 4xx: 16 error-format errors (8 + 8).
  - Spectral's recommended rules add 19 warnings: no `servers`, no `info.contact` or
    `info.description`, and no description or tag on any of the 8 operations.
- **One defect was found in the "fixed" spec, not the draft.** After the first rewrite, `contract
  build` reported one error: `Schema name "ContractFirst.Style.ProblemDetails" must be
  PascalCase`. Root cause: TypeSpec names types declared outside the service namespace by their
  full dotted name. The shared style library lives in its own namespace, so its types needed an
  explicit `@friendlyName`. The same applied to the pagination parameter components
  (`ContractFirst.Style.PageParameters.limit`), which are now `PageParameters.limit`.
- **Detection is complete for the violations the rules target** (140/140) and there are no false
  positives on the compliant spec or the minimal document. This shows the rules do what they say;
  it does not show the style guide covers every inconsistency an API can have.

## Control: what keeps it from regressing

- `make check` in CI: a committed file that differs from the TypeSpec, or any finding at warning
  level or above, fails the build and is shown as an annotation on the line.
- `warn-as-error: true` and the `@typespec/http/all` linter in `tspconfig.yaml`: TypeSpec warnings
  fail the compile.
- Tests tie the rules to their documentation and to a seeded violation each; a rule cannot be
  added or removed without updating both.
- `tsc` strict (with `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`),
  `tsp format --check`, and `npm audit` on every push; exact dependency versions with a committed
  lock file; Dependabot groups TypeSpec and Spectral updates.
